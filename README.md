# air-guitar · 手部关键点检测 + 空气吉他

用摄像头识别手部 21 个关键点，按手势拨响真实吉他采样。
**进度：第一步（手部关键点检测）+ 第二步（发声）都已完成并实机验证。**

**零依赖、零 CDN、零 pip**：模型和 wasm 都在仓库里（约 60 MB），clone 下来就能跑，
不需要 `npm install`，也不需要联网。

---

## 一、怎么跑起来

```bat
git clone <这个仓库的地址>
cd air-guitar
start.bat
```

就这三步。下面是细节。

双击 **`start.bat`**。它会起一个本地静态服务，**等页面真的能访问了再自动打开浏览器**；
关掉那个黑窗口就等于停服务。如果 8765 已经被别的窗口占着，它会直接告诉你
"端口已经有服务在跑了，用这个地址就行"，而不是甩一个 `EADDRINUSE` 崩掉。

或者手动：

```bat
node tools/serve.js 8765
:: 然后浏览器打开 http://127.0.0.1:8765/
```

**打不开的时候先看这两点**：

1. **黑窗口还在吗？** 服务是前台进程，窗口关了、或者从没双击过 `start.bat`，浏览器就是"拒绝连接"。
   也可以看 `http://127.0.0.1:8765/` 是否有人应答：`curl http://127.0.0.1:8765/`。
2. **地址是不是 `http://` 开头。** 直接双击 `web/index.html`（`file://`）一定会失败，
   见下面的警告。

> ⚠️ 不要直接双击 `web/index.html`。ES module + wasm 在 `file://` 下会被浏览器拦，必须走 http。

### 仓库里没有的东西（按需自己取）

为了不让仓库白白胖三倍，下面这些东西**没有**进版本库（`.gitignore` 里写了原因）：

### `start.bat` 里为什么一个汉字都没有

这不是偷懒，是踩过坑：**cmd.exe 解析 .bat 用的是系统 ANSI 代码页（中文系统上是 GBK），
跟文件里的 `chcp 65001` 没关系。** 所以把 UTF-8 的中文写进 .bat，字节会被按 GBK 曲解，
严重时连行尾一起吃掉，整段命令被拆成随机片段，双击后就是窗口一闪、
满屏 `'xxx' is not recognized as an internal or external command`、服务根本没起。

所以：**`.bat` 只放 ASCII，中文提示全部交给 `tools/open_when_ready.mjs` / `tools/serve.js` 打印**
（Node 输出 UTF-8，在 `chcp 65001` 的窗口里显示正常）。
`tools/test_launcher.mjs` 会把这条规则机器化检查一遍：

```bat
node tools/test_launcher.mjs
:: 检查 start.bat 是纯 ASCII、先挂"等就绪再开浏览器"的助手、serve.js 能起来、
:: 小助手能就绪退出、服务不在时会失败（而不是假装成功）
```

打开后：

- 右侧 **「摄像头」** 下拉里选要用的那颗镜头（下面有专门一节讲这个）；
- 点 **「开启摄像头」** → 浏览器会问摄像头权限，允许即可（同时会解锁声音）；
- 或者点 **「样例图片」** 里的任意一张，**没有摄像头也能验证检测**；
- 右侧「发声」里点 **6弦 E / 5弦 A …** 可以直接试听声音，不用摄像头；
- 加 `?selftest=1` 打开批量自检：把全部样例跑一遍，输出每张的检出情况、置信度、伸指数、耗时，并顺带把音频链路（18 个采样解码 + 6 根弦的拨弦调度）验一遍。

```bat
:: 批量自检（无摄像头）
http://127.0.0.1:8765/index.html?selftest=1
:: 手势逻辑自检（全合成数据：会不会响 / 会不会串弦 / 会不会连发）
http://127.0.0.1:8765/index.html?sim=1
:: 只扫一遍摄像头设备名（要一次权限，不会一直开着摄像头）
http://127.0.0.1:8765/index.html?cams=1
:: 打开页面就直接开摄像头（省一次点击）
http://127.0.0.1:8765/index.html?cam=1
```

## 一点五、摄像头怎么选（重要）

**浏览器默认挑的摄像头未必是笔记本内置那颗。** 装了 DroidCam / Iriun / Camo，
或者用了 Windows 11 的「手机连接」，手机就会变成一个系统摄像头设备，
`getUserMedia` 不指定设备时可能就挑到它。

所以页面里做了两件事：

1. **设备下拉**：列出所有摄像头，并按名字打标签——
   `📱 手机/虚拟`（名字里含 phone/手机/droidcam/iriun/camo/virtual 等）、
   `💻 内置`（含 integrated/internal/built-in/hd webcam/front 等）、其余是 `🎥 摄像头`；
2. **默认选中优先级**：用户明确选过的 → **内置镜头** → 第一个不是手机/虚拟的 → 第一个。
   只有用户在下拉框里亲手改过才记进 `localStorage`（键 `airguitar.cameraId.v2`），下次直接用它。
   另外插拔 USB 摄像头会自动重扫（`devicechange`）。

> 这里踩过一个很坑的自我强化 bug：**未授权时设备名全是空的**，代码先瞎挑了一个（手机虚拟摄像头常排在前面），
> 而"开成功之后"又把实际用的设备 id 存进了 `localStorage` —— 于是那个瞎猜被固化成了"用户选择"，
> 之后哪怕能看见"Integrated Camera"这个名字也永远轮不到它。
> 现在：自动挑的结果**不存**；而且只有"上次列举时就已经看得到设备名"时，保留当前选择才算数，
> 否则拿到名字后重新挑一次。

选完不用管，点「开启摄像头」就是它。如果选中的设备打不开（手机断开了之类），
会自动退回系统默认并在诊断行里说明，不会卡死。

实测（就是这台机器）：

## 三、手势怎么弹（已实现）

| 动作 | 含义 |
|---|---|
| 选弦手伸 **1 根**手指 | **1 弦**（最细 e） |
| 伸 **2 根** | **2 弦**（B） |
| 伸 **3 根** | **3 弦**（G） |
| 伸 **4 根** | **4 弦**（D） |
| 伸 **5 根**（五指张开） | **5 弦**（A） |
| **🤘**（拇指 + 小指伸出，其余握起） | **6 弦**（最粗 E） |
| 选弦手握拳 | 没选弦，不发声 |
| **另一只手张开**（2 根手指以上就够） | 拨弦（张得越多越重） |
| **另一只手快速挥动** | 拨弦（适合真做扫弦动作） |
| 另一只手握起 | 闷音（可在界面关掉） |

> **和弦模式下同一套手势换一层含义**：不再是"第几根弦"，而是"**第几个和弦**"
> —— 一律 **伸 n 根手指 = 第 n 个和弦**（☝️ 第 1 个 … 🖐️ 第 5 个，🤘 第 6 个），
> 和和弦按钮上印的编号、键盘 1-6 **完全同一个顺序**。
> 识别层完全没改，换的只是"编号往哪儿查表"。详见「三点五、和弦模式」。

> ⚠️ 闷音这里踩过一个**只有 1 弦会中招**的 bug，值得记一笔：
> 旧代码写的是 `count <= 1` 才算握拳 —— 把"伸出 1 根手指"也当成了握拳。
> 于是"左手 1 根手指选 1 弦"会**每帧都触发闷音**，主音量被压到 0：
> 右手明明张开拨了弦、面板也显示"▲ 拨弦！→ 1弦"，就是一点声音都没有；
> 其余五根弦手指数 ≥ 2 所以完全正常，点弦按钮（不走手势那条路）也正常。
> 修法：`shouldMute()` 只认 `count === 0`，并且**正在选弦的那只手不参与判定**；
> 同时 `GuitarSampler.pluck()` 里先 `unmute()`，保证起音不会被闷音吃掉。
> 现在 `?sim=1` 的第 [14] 组会专门跑这个场景（1 指选弦 + 右手张开必须真的响）。

- **哪只手拨弦默认是"自动（任意手）"**：哪只手做了张开/挥动动作，哪只手就是拨弦手，
  另一只手负责选弦。这样即使 MediaPipe 把左右手标反了（自拍镜像下很常见）也照样能响——
  这是旧版最致命的坑：写死"右手拨弦"时，标反了就怎么动都不出声；
- 拨弦只在**张开的那一瞬间**触发一次，一直举着手不会连发（要收回一点才能再拨）；
- 单手也能弹：先摆好 1-5 根手指，再张开，取的是"张开前那根弦"。

### 屏幕上会亮什么（六弦板）

拨弦的反馈直接画在画面上 —— 弹的时候人是盯着手和画面的，右侧面板的文字**根本不会去看**：

- **六弦板**（画面下方）：6 行 = 6 根弦，从上到下 6→1 弦，每行是
  **手势符号 · 弦号 · 那条弦 · 音名 · 你拨了多少次**；
  - 手势已锁定某根弦但还没拨 → 那一行**淡蓝高亮**（"预选"）；
  - 真拨响 → 那一行**变绿 + 弦抖一下**，计数 +1；
- **画面中央的大字**：拨响瞬间飘出 `🤘 6弦 · A2`，符号就是你要比的手势；
- **TAB 条**：最近 14 次拨弦 —— **这一条就是你刚弹出来的谱子**，
  「复制 TAB」能导出"弦序 + 各弦次数"，方便对着谱子改。

> 这一块 CSS 动画和 class 名必须和 JS 对得上，否则"加了类但什么都不会发生"。
> `tools/test_dom_wiring.mjs` 会逐个核对 class ↔ CSS 规则 ↔ `@keyframes` 三边一致，
> `?sim=1` 的第 [16] 组则在真浏览器里验"拨 6 弦 → 那一行亮、计数 1、TAB 多一格、大字内容对"。

### 整体变调：让 6 根弦对上歌的调

> **2026-10-31 更新：这一段讲的"一次只响一根弦"是**旧状态**，现在已经有和弦模式了（见下面一节）。
> 整把琴不再是六个空弦音，而是 26 个真实和弦指型、一次扫响整个和弦。**

**单音模式下这把琴只有 6 个音高**（`fret` 恒为 0，只有空弦）：E2 A2 D3 G3 B3 E4，
也就是 **Em11 / Am7add11** 那一类和声。而且**一次只响一根弦**（拨弦动作只拨选中的那一根），
所以它是单音乐器 —— 任何歌都得改编，方法见 [tutorial/我不难过-空弦教学.md](tutorial/我不难过-空弦教学.md)。

界面「音频」那一栏加了**整体变调**（−5…+7 个半音，按调名标注）：整把琴一起平移，
平移之后 6 根弦仍然是"主音的 m11"，所以能对上任意一个调。选完之后弦按钮上会直接写上新音名。

| 歌的调 | 变调 | 6 根弦变成 |
|---|---|---|
| E 小调 / G 大调 | 0 | E2 A2 D3 G3 B3 E4 |
| D 小调 / F 大调 | −2 | D2 G2 C3 F3 A3 D4 |
| C 小调 | −4 | C2 F2 A#2 D#3 G3 C4 |
| A 小调 / C 大调 | +5 | A2 D3 G3 C4 E4 A4 |
| B 小调 | +7 | B2 E3 A3 D4 F#4 B4 |

> 实现上有个容易写错的地方：**变调不能去换采样文件**。仓库里只有 18 个空弦录音，
> 变调是靠 `playbackRate` 升降（`web/js/audio.js` 的 `fret + transpose`），
> 取哪个 wav 永远按**原来的**音名。写成"用新音名去找采样"就会变成"找不到这个音"。
> `?sim=1` 的第 [15] 组专门验这个：4 个变调 × 6 根弦 = 24 种组合都要能取到采样并报出正确音名。

> 顺带纠一个我自己写错过的标注：`−3` 不是 C 小调（E 降 3 个半音到 **C#**），
> `−4` 才是 C 小调。`node tools/test_dom_wiring.mjs` 现在会把 13 个选项的调名逐个核对。

## 三点五、和弦模式：治"音色单调"

**先说清病根。** 有人反馈"声音单调"，我去查了引擎，发现原因不是音色，是**一次只响一个音**：

```js
// web/js/audio.js —— 早就写好了，但主程序从来没用过
strum(stringIndices, {velocity, spreadMs, down, fret})  // 把一组弦依次拨出来 = 和弦
playbackRateForFret(fret)                                // 每根弦按第几品 → 变音高
```

而 `web/js/app.js` 的 `handleStrum()` **从头到尾只调 `pluck()` 一根弦，而且 `fret` 永远是 0**。
所以"按一个 C 和弦"实际只响了一个空弦音 —— 和弦的另外两个音根本没地方响。这就是单调。

改完之后有三件事：

| 加的东西 | 具体是什么 | 在哪 |
|---|---|---|
| **和弦齐奏** | 一次手势/按键 → `strumChord()` 按指型把 3~5 根弦扫出来 | `audio.js` |
| **按品** | 每根弦按第几品由指型决定，**不再被那 6 个空弦音锁死** | `chords.js` |
| **混响** | 卷积混响，脉冲响应程序合成（不用外部文件，离线可用） | `audio.js` |

### 和弦表：26 个手写指型 + 12 个调的大横按族（`web/js/chords.js`）

`frets` 一律是 **[6弦, 5弦, 4弦, 3弦, 2弦, 1弦]**，`-1` = 不弹该弦，数字 = 品位。
按法就是真实吉他的按法：

```
C       x 3 2 0 1 0     C E G C E
Fmaj7   x x 3 2 1 0     F A C E
G       3 2 0 0 0 3     G B D G B G
Am7     x 0 2 0 1 0     A E G C E
Gsus4   3 3 0 0 1 3     G C D G C G
G/B     x 2 0 0 0 3     B D G B G     （转位，用来接到 Am）
```

**这些和弦对不对是机器证明的，不是我说了算。** `node tools/test_chords.mjs` 会
用标准调弦**算出每个指型的真实音高**，然后逐条验证：

- 有没有**和弦外的音**（错音）；
- **根音**必须在；
- 决定大小三和弦的**三度音**必须在（不然"大三写成小三"根本发现不了）；
- 七和弦的**七度音**必须在；
- 转位和弦（`G/B`）的**最低音**必须是声明的那个低音。

`220 项全过`，并打印一张对照表（指型 → 组成音 → 音级）供肉眼复核。

### 变调 = 夹变调夹（这里踩过一个坑，值得记）

**坑长什么样**：和弦库写着「抒情走向（C Am F G Em Dm）」，但选了它之后按钮上显示的是
`F Dm A# C Am Gm` —— **显示和库名对不上**。

**原因**：我把「整体变调」理解成"把和弦名字整体移调"了。变调 +5 时把 `C` 显示成 `F`、
`Am` 显示成 `Dm`……名字全变了，用户当然不知道哪个是哪个。

**而变调的真正含义是夹变调夹**：

> 你想听到 **C** 和弦，夹 5 品时应该**改按 G 指型**（G 上移 5 品 = C）。
> **听的和弦不变，变的是"按哪个形状"。**

所以现在：**和弦库定义"要听到的和弦"（= 谱子上的写法），变调只决定"按哪个指型"**。

| | 显示（要和弦库一致） | 实际按的指型 |
|---|---|---|
| 变调 0 | C Am F G Em Dm | C Am F G Em Dm |
| 变调 +5 | **C Am F G Em Dm** | G Em C D **Bm Am** |

指型和显示名不一样时，界面上会跟在和弦名后面标出来（`C ↦G`）。
这样"和弦库 ↔ 屏幕 ↔ 谱子"三者永远对照，而音**始终是你要的那几个和弦**。

12 个调 × 5 种和弦类型（大三/小三/属七/小七/大七）的指型没有手抄 60 个（一定会抄错），
而是从 **E 型 / A 型两个空弦模板机械平移**出来的（`BARRE_FAMILIES`），
再按"把位最低"挑一个。`test_chords.mjs` 会把
**和弦库 × 变调 −12…+12 共 600 个组合**全部算一遍，验证：

1. 显示名**永远**等于和弦库里的写法（这就是"对照"的定义）；
2. 每个组合都找得到指型（12 个调全覆盖）；
3. 把那个指型整体上移变调数之后，**音级正好等于想听的和弦**。

三条都是上面那个坑的**反向测试**——修好了，而且以后不会再退回去。
万一某个和弦类型在某个变调下确实没有指型，界面会**如实标出来**（变灰 + 划掉指型），
绝不会偷偷换个和弦糊弄过去。


### 怎么弹

- 勾上「**和弦模式**」→ 六弦板从"6 根弦"变成"**6 个和弦**"（显示 **编号** + 和弦名 + 指型 + 扫了几次）；
- **手势完全不重新学**：还是"一只手伸手指选 + 另一只手张开扫"，只是"第几根弦"变成"第几个和弦"
  —— 复用的就是原来那条识别链路，**识别层一行没改**；
- **三种入口共用同一套编号**（都是 1 = 第 1 个和弦）：

| 入口 | 第 1 个 | 第 2 个 | … | 第 6 个 |
|---|---|---|---|---|
| 手势 | ☝️ 1 指 | ✌️ 2 指 | … | 🤘 |
| 和弦按钮 | 印着 `1` | `2` | … | `6` |
| 键盘 | `1` | `2` | … | `6` |

> ⚠️ **这里也踩过一个坑**（你报的"和弦模式下高亮行和手指对不上"就是它）：
> 和弦模式一开始图省事，沿用了弦模式的逆序（`槽位 = 6 - 手指数`），
> 于是"**伸 1 指**"选中的是**第 6 个**和弦。可和弦按钮上印着 `1 2 3 4 5 6`、
> 键盘 1-6 又是从第 1 个开始 —— **同一套编号出现两个含义**，
> 屏幕上高亮的那一行当然"和手指对不上"，听起来也像弦号识别错了。
> 修法：和弦模式统一成 **伸 n 指 = 第 n 个**（`slotFromStringIndex(s) = 5 - s`），
> 并把和弦板的**行序符号也跟着倒过来**（第 1 行是 ☝️），
> 这样"**行的符号 = 你要比的手势**"和"**n 指 = 第 n 个**"两条同时成立。
> `?sim=1` 的第 [17] 组会验这个顺序不变式（还验"伸 2 指"和"按键 2"落到同一个和弦）。

- 「和弦库」下拉决定这 6 个槽位是哪 6 个和弦，内置 4 套：

| 和弦库 | 6 个槽位（槽1 → 槽6） |
|---|---|
| C 调常用 | C G Am Em F G7 |
| 七和弦 | Cmaj7 G Am7 Em7 Fmaj7 Dm7 |
| 抒情走向 | C Am F G Em Dm |
| 小调 | Am F C G Dm E7 |

> 拉下和弦库时，**屏幕上显示的永远就是这一串**（不管变调设成几）。
> 这是有测试守着的：`test_chords.mjs` 会核对"下拉标签里写的和弦"和"槽位里实际存的"
> 是否逐字一致 —— 标签不许说谎。

- 「全部和弦」区列出**所有 26 个**和弦，不在槽位里的也能点着弹（换调、借和弦时用）；
- 「混响」滑块 0-60%（默认 22%）。滑块拖的时候用 `setTargetAtTime` 平滑过渡，不会"啪"一下。

### 证据（两条，都不用你信我）

**一、能听出来。** [tutorial/demo-和弦对比.wav](tutorial/demo-和弦对比.wav)（25.5 秒）连着三段，
同一组走向 `C G Am F`：

| 段 | 内容 |
|---|---|
| 第 1 遍（0-7 拍） | **单音**：每次只响 1 个音 —— `C→E  G→G  Am→A  F→A`（这就是之前听到的） |
| 第 2 遍（8-15 拍） | **和弦齐奏**：每次响 5 根弦 |
| 第 3 遍（16-31 拍） | **和弦齐奏 + 混响**（和网页里**同一个**脉冲响应） |

单音那一段已经是"现状能给出的最好结果"了（从空弦音里挑一个和弦音，优先根音→三度→五度）。
注意 `F`：空弦音里**根本没有 F**，只能拿 3 度音顶替 —— 这就是旧模式的极限。

**二、频谱能测出来。** `node tools/probe_chroma.mjs` 从**音频本身**反推每段的音级能量，
不依赖渲染时用的那份指型表（否则就是拿定义证明定义）：

```
──── 单音（现状） ────
  ✓ C   期望 {C E G}  最响的那个音：E60% B34% G#4%      ← 只有一个和弦音
──── 和弦齐奏 ────
  ✓ C   期望 {C E G}  最强 3 个：E38% G29% C23%         ← 三个和弦音都在
  ✓ G   期望 {G B D}  最强 3 个：D37% G27% B23%
  ✓ Am  期望 {A C E}  最强 3 个：E37% A29% C20%
  ✓ F   期望 {F A C}  最强 3 个：F44% A25% C18%
```

（混响段的判据放宽成"和弦音都要在"：前一个和弦的混响尾巴还响着，
带出它自己的音是**正常的**，不是错。这也是为什么示范里加混响那一段放慢到一小节一个和弦 ——
混响需要空隙，排太密会糊在一起。）

### 混响的脉冲响应也是可验证的

脉冲响应是程序合成的（`impulseData()`，固定种子的伪随机数，两次生成结果一致），
所以它能在 Node 里直接测：单调衰减、双声道不同、无 NaN、1.8 秒长度。

离线示范音频里的混响用的是 **FFT 卷积**（`tools/convolution.mjs`）——
朴素卷积是 87000 × 79000 ≈ 69 亿次乘加，纯 JS 要跑几分钟。
`node tools/test_convolution.mjs` 把它和**朴素卷积**逐点比对（22 项全过）。
容差写的是 `FLOAT32_EPS`：输出是 `Float32Array`（写 wav 用），
允许的误差上限就是 float32 的舍入精度，实测各尺寸都在 3e-8 左右；
真要是分块叠加的偏移算错了，误差会是 O(1) 量级，一眼就能抓到。

### 还没做的

- **扫弦方向/节奏型**：现在是一次扫出整个和弦，还没有"下上下上"这种自动伴奏；
- **按品只服务和弦**：单音模式下 `fret` 仍然是 0（想弹旋律还得靠变调）；
- 《情歌》的**具体走向**没有写死成"一键伴奏"：谱子我读不到（见「环境备注」），
  但 C 调需要的和弦（C Dm Em F G Am G7 + 七和弦色彩）现在全都能弹了，
  照着谱子按 1-6 或点和弦就行。你把走向给我，我可以再做"按一下自动走一遍"。

### 为什么"不灵敏 / 乱串弦"——已经修的四层
单帧的伸展度直接拿去判弦是不可能稳的（手指在半屈状态会一帧伸一帧握）。
现在每只手的判定都过了四层，全在 `web/js/landmarks.js` 里，Node 可单测：

| 层 | 作用 |
|---|---|
| **EMA 平滑** | 一帧抖动不会直接改变结果 |
| **逐指滞回** | 进入"伸出"要 ≥ 阈值，退出要 < 阈值−0.15，中间区间保持原状 |
| **时间投票** | 最近 5 帧里至少 3 帧同意才算数 |
| **结果锁定** | 投票没通过时保持上一根弦，绝不闪断 |

另外伸展度本身也换了算法：关节夹角 **+ 指尖到手腕的距离/掌长** 两个线索加权融合
（光看夹角时，"弯着但没握起来"会被误判成伸出）。

### 不灵敏怎么调（按推荐顺序）

**第 0 步（最有效）：先做一次手势校准。**

点右侧「**手势校准（推荐做一次）**」，然后按提示把 6 个手势各比划一次（每个保持 2 秒左右，全程约 20 秒）。
它会把**你自己手的伸展度**存下来，之后按"最像哪一次校准"来判，而不是套用固定规则。

这一步能直接消掉的症状（都是实测踩到的）：

| 症状 | 原因 | 校准/新规则后 |
|---|---|---|
| 比划 **1 指**（食指）却响 2 弦或干脆不响 | 一伸食指，拇指跟着翘过阈值，被数成 2 根 | 按你的模板判 → 1 弦 |
| 比划 **🤘** 有时响 **1 弦** | 拇指漏判时 🤘 只剩小指，被数成"1 根" | 判据不再依赖拇指 → 6 弦 |
| 比划 **🤘** 面板显示"伸出 2 根" | 🤘 本来就是 2 根（拇指+小指），显示根数不代表判错 | 声音一直是 6 弦 |
| **只有 1 弦"显示触发了却没声音"** | 不是校准能解决的，是闷音判定的 bug（见第三节的说明） | `shouldMute` 已修：伸 1 根手指不再算握拳 |
| **手指数显示是对的，但弦号/和弦全不对应**（1→3、2→6、5→3、🤘→1） | 校准模板最近邻和手指数是**两条独立的路**，而 `maxDist=0.7` 太松，几乎每帧都命中某个模板 → 判定跟手指数脱钩 | 见下面「校准模板的两道闸」 |

校准结果存在浏览器本地（`localStorage`），换浏览器/清了缓存要重做一次。
做完会显示「最小模板间距」——**这个数越大越不容易串弦**；小于 0.3 会提醒你
"两根弦的姿势太像"，就把手势做得更开一点。

#### 校准模板的两道闸（"手指数对但弦号全错"的治本）

这是本项目**最难查的一个 bug**，因为屏幕上两条信息可以同时"看着都对"：

- **"伸出 n 根"** 来自滞回后的布尔数组 `t.up`（所以你看到的根数是对的）；
- **查表用的弦号** 来自 `classifyByTemplates()` 的最近邻，和 `t.up` **没有任何关系**。

于是"伸出 1 根"和"判定 3 弦"能同时成立 —— 表现就是"手指数显示正确，但对应全错"。
更糟的是原来的 `templateMaxDist = 0.7`：在 5 维单位区间里，五根手指平均差 0.31
就算"像"，所以**几乎每一帧都能命中某个模板**，判定等于从 6 个模板里随机挑。

现在三道闸：

1. **距离上限收到 0.45**，离模板太远就退回内置规则（不再"谁都像"）；
2. **要求 margin**（默认 0.08）：候选模板必须明显比第二像的更像，**打平就不采信**；
3. **同源**：采信模板时，判定结果连"手指数"一起给（`countAsJudged`），
   并算出 `judgedAgrees` —— 界面必须在"判定和手指数打架"时**明说**，
   而不是悄悄改口径：面板会红字提示「⚠ 判定和手指数不符：看到伸 1 根（= 1弦），
   但校准模板给的是 3弦 —— 点「清除校准」重新比划一次」。

一眼分清是模板还是规则的开关：**`?nocal=1`**（本次会话不加载校准模板，存储里的不删）。

`test_landmarks.mjs` 的 **[14.5]** 组是这个症状的反向测试：退化模板（6 个几乎一样）
必须退回规则、判定弦号和判定手指数必须永远一一对应（🤘=第 6、其余 = 6−弦号）、
模板和手指数打架时 `judgedAgrees` 必须为 false。

**第 1 步：如果还串，换「弦映射」= 方案B。**

方案A（你原本的设计）拇指算一根，伸 N 指 = N 弦；
方案B **只数食指/中指/无名指/小指**，拇指只在 4 弦/5 弦这一处起作用。
拇指是五根里最难判稳的一根，把它从计数里拿掉能立刻压住 1/2 弦和 4/5 弦的串扰。

**第 2 步：调「伸指阈值」。**

伸展度条上的**橙线**是阈值、**白线**是平滑后的当前值（值变绿 = 判定成伸出）。
手指伸出来白线却够不到橙线 → 往左拉；握拳时白线还压在橙线上 → 往右拉。

**第 3 步：「触发方式」。**

`张开 或 挥动`（默认，最灵敏）/ 只认张开（最稳）/ 只认挥动（适合真扫弦）。

### 不发声时先看「演奏状态」面板

右下方那块会实时写清楚**为什么不响**，比如：

```
左手：伸 2 根→2弦 B（张合+0.12 速度0.4）　右手：伸 0 根（张合+0.00 速度0.0）
要发声：选弦手已锁定 2弦 B；另一只手张开或挥一下
```

或 `拨弦动作识别到了，但没选到弦：先伸 1-5 根手指选弦，再张开拨弦`、
`没看到手。把手放进画面里，光线亮一点。`、`采样音色还没加载好。点一下「6弦 E」…`。

发声用的是 **University of Iowa 的真实木吉他采样**（见第六节），
每个音 3 个力度层（pp/mf/ff），按拨弦力度自动切换。

## 五、为什么现在用的是 MediaPipe，handpose_x 什么时候上

你给的 **handpose_x 是"关键点回归"模型**，作者 README 第 39 行写明：

> 注意：该项目不包括手部检测部分.

它需要先有人给出"手在哪"的方框，再把手图裁成 256×256 喂进去。而它的**预训练权重不在仓库里**（我确认过仓库和作者另一个仓库 `onnx_run` 都没有 `.pth`/`.onnx`，HuggingFace 上也没有可用镜像），只在百度网盘，密码 `99f3`。

所以现在这样分工：

| 环节 | 现在 | 权重到位后 |
|---|---|---|
| 手在哪（检测） | MediaPipe 手掌检测 | 不变，MediaPipe 出框 |
| 21 关键点 | MediaPipe HandLandmarker | **handpose_x**（onnx 走 onnxruntime-web，不用装 PyTorch） |
| 手势→发声 | 已实现（MediaPipe 关键点） | 不变 |

裁剪规则已经按作者 README 实现好了（`bboxFromLandmarks`：`w = max(|x2-x1|,|y2-y1|) × 1.1` 的方形框），参数和 `inference.py` 一致。你按 [`docs/权重获取清单.md`](docs/权重获取清单.md) 把模型包丢进 `incoming/`，我就把第二个引擎接上。

## 六、吉他采样是怎么来的（可复现、可校验）

发声用的是 **University of Iowa Musical Instrument Samples (MIS)** 的木吉他采样
（mono 16bit/44.1k，免费使用，**需署名 University of Iowa Electronic Music Studios**）。

Iowa 的采样是按"音域段"打包的：一个 aif 文件里含一串音，中间用静音隔开，
所以不能直接拿来用。`tools/fetch_guitar_samples.py` 做了这么一条流水线：

1. **自己解码 AIFF**（Python 3.13 删了 `aifc`，索性直接读 FORM/COMM/SSND 块）；
2. **去直流和低频轰鸣**（作者 pp 那几条有明显的地震级低频，会把音符盖掉）；
3. **按 RMS 包络切音符**；
4. **自相关测基频 + 八度纠错**：自相关会把 B3(247Hz) 认成 122Hz、把高音认成次谐波，
   所以再用频谱确认"这个频率到底存不存在"（低音弦基频可能只有峰值的 5%，但一定存在）；
5. **先按音准选、再按余音选**（顺序反了会选到别的音，见下面「五弦事件」）；
6. **重采样校正到标准音高**：原录音整体偏低 1.7%（≈29 音分），全部校正掉；
7. **写出后重新读回来复测基频和余音**。

最终 18 个音（6 弦 × pp/mf/ff）的实测偏差**全部 ≤ 0.05%**，这条流水线每次跑都会重新打印校验表。

### 五弦事件：为什么"音高全对"的采样听起来却不对

用户反馈：**"五弦很明显的和另外五根区别很大"**。

查下来是这样——`check_samples.mjs` 一开始说 18 个文件的音高最大只差 4 音分，**全对**。
但它的检查项只有音高、峰值、时长，于是漏掉了一个东西：那张表里

| 时刻 | A2（5 弦） | D3（4 弦，同层对照） |
|---|---|---|
| 0.05s | −9.5 dB | −16.3 dB |
| 0.25s | **−24.2 dB** | −18.2 dB |
| 0.50s | −35.4 dB | −21.1 dB |

A2 **250 毫秒掉了 15 dB，然后停在 −36 dB 不再衰减**——这形状不是"弦在振动"，
而是"弦被手按住了"。原始录音里那条 `ff.sulA.A2B2 #1` 就是这么弹的。

两个独立的毛病叠在一起：

1. **切段规则把尾巴砍了**：判定静音的阈值是"峰值的 6%"，而吉他余韵衰减到 −25 dB
   以后就在这个阈值附近抖动，于是切段提前结束；代码又用 `end + 0.4s` 当结束点，
   结果 A2 只留了 0.64 秒。
   → 改成**按"起音点 + 固定 2.6 秒"取长度**，只要不撞上下一个音的起音点就留满。
2. **`ff` 层那条 A2 是被闷掉的**，而且整个包里没有更好的 ff 版 A2。
   → 加了「余音」判据（0.45~0.65s 处相对起音的电平），并允许**只在明显被闷掉时**
   从别的力度层借同音的一条（`ff/5弦` 现在借的是 `mf` 层的空 A 弦）。

顺带还发现 `pp/1弦 E4` 也是同样被闷掉的短音（用户没提，但同一个病），一起修了。

修完对照（同一套判据跑旧文件抓出 **25 处问题**，跑新文件 **0 处**）：

| | 旧 | 新 |
|---|---|---|
| 6 弦各音时长 | 0.64 ~ 2.60 秒 | **2.54 ~ 2.58 秒** |
| 5 弦余音（0.5s 处） | −28.7 dB | **−13.1 dB** |
| 同层内余音互差 | 最大 23 dB | **≤ 12 dB** |

三个自查工具：`tools/check_samples.mjs`（音高/时长/余音/同层一致性，`--dir` 可指向别的目录）、
`tools/probe_candidates.py`（列出某个音的所有候选及衰减）、`tools/probe_envelope.py`（打印原始包络）。
其中 17 个用的是空弦本弦的录音（音色最正），只有 ff 层的 1 弦因为原始录音偏了 4.9% 换用别的弦上同一个音。

## 七、环境备注（踩过的坑）

- 本会话是 DSH 的 `workspace-write` 沙箱，**pip 装不进工作区**（连 `six` 都报 `Errno 13` + `file access denied under workspace-write`），`venv` 的 `ensurepip` 同样过不去。
  所以整套东西**没有引入任何需要 pip 安装的依赖**：模型和 wasm 是直接用 `urllib` 下到 `web/vendor/` 的，采样处理只用了 Anaconda 里已有的 numpy。
- `git`、`curl` 在这个沙箱里 TLS 是坏的（`schannel: SEC_E_NO_CREDENTIALS`），下载统一走 Python 的 `urllib`。
- **网页版 `web_search` 是坏的**（`HTTP 401 api key invalid`），所以**网上的吉他谱我读不到**。
  试过并全部失败的路子：`web_fetch`（页面正文抓不全，和弦多半是图片）、`curl.exe` 和
  `Invoke-WebRequest`（TLS 被沙箱挡）、读用户浏览器窗口的 UIA 树（Edge 只暴露标题栏）、
  `r.jina.ai`（fetch failed）。
  **结论：本项目的歌曲和弦走向一律由用户提供，我没有"凭印象编一份"过。**
  想要"一键伴奏某首歌"，把和弦名贴给我就行（比如 `C G Am F`）。
- 摄像头必须在窗口前台才能拿到画面；后台跑浏览器不会给视频流。
- 浏览器的自动播放策略：没点过页面时 `AudioContext` 是挂起的，点"开启摄像头"或任一根弦就会解锁。
- 本会话的模型**不支持图片输入**，所以看不了谱子截图、也看不了页面截图，只能靠文本和数值验证。
- `incoming/Guitar.mono.1644.1.zip`（120MB）是采样的原始包，删了也能重新下，但要重跑 `tools/fetch_guitar_samples.py`。
